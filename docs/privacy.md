# Privacy

Varnqor is local-first by design.

## Default boundary

Varnqor does not require a Varnqor cloud account or provider API key for local analysis. Its default product boundary is:

- no prompt upload;
- no source-code body upload;
- no assistant-response upload;
- no raw tool-result body persistence;
- no hidden background data export;
- no product telemetry required for local analysis;
- read-only access to supported agent session data;
- no external agent action executed automatically by Optimize or Control Plane.

Investigate, Missions, Pulse, Advisor, Optimize and Control Plane operate on local resource metadata. Themes, translations and provider identification marks are bundled locally and require no runtime CDN.

## What the usage index stores

For supported providers, Varnqor stores resource/accounting metadata needed for observability and control decisions:

- provider;
- timestamp;
- model label when available;
- project/workspace label when available;
- session identifier;
- subagent flag when the provider exposes it;
- input/output/cache token counts;
- source-file path and source offset used for incremental indexing.

Observed session files and token-bearing usage remain different concepts. A local session can exist without producing a token usage row.

## Claude tool metadata

Claude Code currently has the deepest tool-level adapter. For explainable Waste rules, Varnqor may store:

- tool name;
- timestamp;
- project/session identifiers;
- file or safe scope path when exposed by tool input;
- Read offset/limit;
- tool-result byte length;
- error state;
- SHA-256 fingerprint of canonical tool input.

Raw tool input is discarded after fingerprinting. Varnqor does not persist prompt text, assistant text, file contents, tool-result text, Bash commands, Grep patterns, or Write/Edit payloads in the tool index.

The fingerprint exists only to compare whether two local operations had the same canonical input. It is not encryption and is not uploaded by default.

## Optimize

Optimize reads the same local usage and privacy-minimized Waste metadata used by the rest of Varnqor. It computes target scenarios and bounded playbooks locally.

Optimize does not silently:

- rewrite a prompt;
- switch a provider or model;
- stop or launch an agent;
- execute a tool;
- mutate a repository;
- change provider credentials or limits.

`preview` and `manual` describe presentation of the plan. They are not remote execution permissions.

Estimated impact ranges are heuristic and may overlap. They are not represented as guaranteed savings.

## V4 Control Plane

The V4 Control Plane combines existing local evidence into three derived object types:

- **Missions** — operational classification of recent provider/session activity;
- **Incidents** — deterministic policy-threshold crossings or provider-health problems;
- **Decisions** — reviewable interventions derived from incidents and Optimize playbooks.

These objects are computed locally. A mission does not mean Varnqor owns or controls the underlying provider process. Control state does not grant permission to execute against Claude Code, Codex, Gemini CLI, a repository, or the operating system.

The Control Plane can use a user-configured local token budget for runway/risk decisions. That budget is not provider quota data and is labeled accordingly.

## Control Brief

`varnqor brief` and the desktop **Copy control brief** action generate a portable markdown summary from Control Plane output.

A Control Brief may contain:

- selected range and resource pace;
- provider/project/session identifiers already present in the resource index;
- mission counts/state;
- incident titles and explanations;
- decision titles, evidence and bounded impact ranges;
- review steps generated by deterministic Varnqor logic.

A Control Brief does **not** reconstruct or include prompt text, assistant responses, source-code bodies or raw tool-result bodies because Varnqor does not persist those bodies in the analytics index.

Copying a brief places that generated text on the user's local clipboard. Varnqor does not automatically send the brief to an external agent or service.

## Codex and Gemini

Codex and Gemini adapters index usage/resource metadata from supported local session formats. They do not currently contribute tool-level Waste findings.

Codex compressed `.jsonl.zst` archives are detected and reported as unsupported rather than silently decoded or ignored.

## Local storage and preferences

Historical metadata is stored in Varnqor's local SQLite database under the user's application configuration directory. Settings are also local and include:

- refresh interval;
- configured budget;
- Pulse guardrails;
- language;
- appearance preference;
- Optimize strategy and target scenario;
- V4 Control Plane policy profile and thresholds.

Settings migrations preserve supported previous-version preferences while filling new fields with documented defaults. V4 preserves an explicit Light selection; previous System/default appearance is migrated to the V2-dark product identity.

## Future online features

Any future feature that sends Varnqor data off-device must be explicit, opt-in and documented separately. Local analysis and decision support should remain useful without an online service.
